# 字节级BPE分词

**字节级 BPE（byte-level Byte Pair Encoding）以字节为基础单位，通过合并频繁出现的片段，在广泛文本覆盖能力与较短的词元序列之间取得折中。** 本笔记解释 GPT2 为什么采用它，以及“256 个基础字节”和“50,257 个词表词元”为什么并不矛盾。

本文依据 [[language-models-GPT2.pdf]] 第 2.2–2.3 节及 OpenAI 发布的 GPT2 分词实现整理。论文中的表示选择与数值、实现中的精确分块规则、教学示意和实际编码结果分别标明；实际结果使用官方 `encoder.py` 及 124M 模型发布的 `encoder.json`、`vocab.bpe` 核验。

## 为什么不直接按词处理

传统词级语言模型通常只有一个有限词表。罕见词、新名字或某些符号可能变成 `<UNK>`；小写化、固定分词等预处理也可能丢掉原始信息。

如果目标是对广泛来源的文本建模，这些限制就很麻烦。模型理想上应该能够为任意字符串分配概率，而不是只能处理预先规定的一部分词。

## 为什么不直接把每个字节都当一个词元

Unicode 文本编码成 UTF-8 字节后，基础字节只有 256 种，覆盖起来很容易。但完全按字节处理，常见的长词也要拆成许多预测步骤；作者发现标准字节级语言模型在 WebText 上的效果仍不如词级模型。

BPE 提供了折中：频繁出现的片段可以合并成一个词元，少见片段保留较小单位。它不像固定词表那样要求每个词都是已知的，也不像纯字节模型那样总把常见词拆得很碎。

## GPT2为什么强调“byte-level”

GPT2 论文第 2.2 节指出，很多名为 BPE 的实现实际上以 Unicode 码点为基础，而非字节。若要覆盖所有 Unicode 符号，基础词表就可能超过 13 万；这已经大于常见 BPE 最终词表的规模。

GPT2 的字节级 BPE 以 256 个字节值为基础，再学习频繁片段的合并，最终词表为 50,257。**256 是基础字节集合的大小，50,257 是模型使用的词表大小，两者不是相互冲突的数字。**前一个数字来自第 2.2 节的输入表示说明，后一个数字来自第 2.3 节的模型规格。

可以用一个不依赖具体分词器输出的例子理解：一个常见英文单词可能被合并成较少的词元，陌生姓名则拆成几个片段，极少见字符也可以退回其字节表示。这里只解释设计思想，没有声称某个具体单词在实际 GPT2 分词器中必定怎样切分。

## 为什么限制跨字符类别的合并

BPE 按频率贪心合并，若不作限制，就可能把 `dog`、`dog.`、`dog!`、`dog?` 等分别占据词表位置。这会为“同一个词搭配不同标点”花掉大量词表容量。这组词形是论文第 2.2 节用于说明问题的例子，与上节另行概括的姓名示意不同。

论文将此概括为“阻止跨字符类别合并，并为空格设置例外”。**空格例外的精确含义是：一个普通前导空格可以与后面的字母、数字或标点／符号进入同一预分块，BPE 可以在块内把它们合并；并不是允许任意跨越空格，把前后两个单词合成一个词元。**论文正文未列出完整表达式，下面的细节来自已核对的官方实现。

最终效果是尽量兼顾词级模型的预测效率与字节表示的覆盖范围。它让模型能够评估采用不同分词、预处理或词表的数据集，但**不代表任何语言都已获得同样好的语言能力**。输入覆盖能力与训练数据提供的能力不同。

## 空格例外：可以带上前导空格，但不能越过预分块

官方分词过程先用正则表达式切出若干块，再对**每一块分别**做 UTF-8 编码、字节映射和 BPE。因此，两种边界要分清：

1. **预分块边界**决定哪些字符有机会进入同一次 BPE；不同块之间不能合并。
2. **块内合并规则**决定哪些相邻片段实际合并；同一块不保证最终只有一个词元。

正则中与空格例外直接相关的三类分支如下，仅摘选关键部分：

```regex
 ?\p{L}+
 ?\p{N}+
 ?[^\s\p{L}\p{N}]+
```

它们分别匹配字母串、数字串、非空白且非字母数字的符号串，前面都可以带**至多一个普通 ASCII 空格 U+0020**。完整正则还处理缩写和独立空白；这里的前导空格不是任意空白的 `\s?`，所以 Tab、换行不通过这个例外附着到后面的单词。

下表是正则得到的**预分块**，不是最终词元。引号内开头的空格是文本的一部分；`\t`、`\n` 分别表示 Tab、换行。

| 原始文本 | 预分块 | 含义 |
| --- | --- | --- |
| `ab` | `["ab"]` | `a` 与 `b` 在同一块，有机会合并 |
| `a b` | `["a", " b"]` | 两个字母处于不同块，不能跨块变成 `ab` 或 `a b` |
| `hot dog` | `["hot", " dog"]` | 空格归入后一个块，不把两个单词串成同一块 |
| `dog.` | `["dog", "."]` | 字母与句号分块，不能直接合成 `dog.` 词元 |
| ` dog.` | `[" dog", "."]` | 前导空格可附着到字母块，句号仍独立 |
| `abc123` | `["abc", "123"]` | 字母与数字也有分块边界 |
| `a  b` | `["a", " ", " b"]` | 两个空格不会都附着到后面的字母块 |
| `\tdog` | `["\t", "dog"]` | Tab 与字母分块 |
| `\ndog` | `["\n", "dog"]` | 换行与字母分块 |

纯空白块内部仍会进入 BPE，因此也不要把规则概括成“任何空白都永远不能合并”。要判断能否合并，先看是否跨越了正则匹配块，再看块内是否有相应合并规则。[官方预分块及编码实现](https://github.com/openai/gpt-2/blob/master/src/encoder.py#L48)

### 实际编码与空间压缩

官方 GPT2 编码使用 `Ġ` 作为普通空格字节的可见映射符号。它不是原始文本额外添加的字母，解码时会还原为空格。

| 输入 | 实际词元字符串 | 词元 ID |
| --- | --- | --- |
| `dog` | `["dog"]` | `[9703]` |
| ` dog` | `["Ġdog"]` | `[3290]` |
| `hot dog` | `["hot", "Ġdog"]` | `[8940, 3290]` |
| `dog.` | `["dog", "."]` | `[9703, 13]` |

` dog` 能由一个词元表示，说明空格确实可以和后面的单词片段合并。若必须把空格单独表示，就还需要一个空格词元；把常见“空格＋单词”组合压到一个词元可以减少序列长度。这仍然没有让 `hot dog` 跨两个预分块合为一个词元。

上述结果是运行官方编码函数和发布的分词数据得到的核验结果，不是随意设定的教学 ID。[官方词表数据](https://openaipublic.blob.core.windows.net/gpt-2/models/124M/encoder.json)

## 词表会同时包含a、b和ab吗

**会，而且官方 GPT2 词表确实如此。**这里说的是“词元／片段”，不要求它们都是自然语言中的完整单词。

| 词元字符串 | 官方 GPT2 词元 ID |
| --- | --- |
| `a` | 64 |
| `b` | 65 |
| `ab` | 397 |

可以用以下教学示意理解 BPE 词表扩展：

$$
V_0=\{a,b,\ldots\},\qquad
V_1=V_0\cup\{ab\}.
$$

学习到 $a+b\rightarrow ab$ 时，增加的是可以表示更长片段的词元；并不是从词表删除 `a` 和 `b`。它们在独立出现或其他片段的编码中仍可能需要使用。应区分**替换某次分词序列中的两个相邻位置**，与**删除整个词表里的两个旧词元**。

子词 BPE 的词表可以保留不同长度、内容重叠的片段；Sennrich 等人的第 3.2 节以“初始符号数加合并操作数”说明词表扩展，GPT2 的发布词表也直接验证了这个共存例子。[子词 BPE 原始论文](https://arxiv.org/pdf/1508.07909)

## 词表有重叠，编码时会不会随意选

**标准 GPT2 BPE 不随机在 `["ab"]` 与 `["a", "b"]` 之间选择，也不是简单的最长词表匹配。**推理时不重新统计当前文章中的片段频率，而是使用训练时已经学到、顺序固定的合并规则。

在同一个预分块中，算法先从字节映射后的基础符号开始，反复选当前相邻符号对中合并排名最靠前的一对，应用合并后再计算下一步，直到没有可用规则。官方 `bpe_ranks` 由发布的合并表顺序产生。

对于独立输入 `ab`，官方分词器确实把它编码为 `[397]`，即一个 `ab` 词元。对于 `a b`，预分块已经不同，实际得到 `[64, 275]`，对应 `a` 与带前导空格的 `Ġb`。对于更长输入，其他相邻对可能先合并，因此不能只因为词表存在 `ab`，就推断凡包含这两个字符的文本都一定使用 `ab` 词元。[官方块内 BPE 合并循环](https://github.com/openai/gpt-2/blob/master/src/encoder.py#L50)

## 标点、符号与字母之间的边界

这里讨论的是 GPT2 的普通文本分词，不是模型专用控制词元（例如 `<|endoftext|>`）。`&`、`,` 都属于正则中的非空白、非字母、非数字分支，不能与旁边的字母串跨预分块合并。一个字符串在语义上是否被当作“一个词”，与它能否编码成“一个词元”是不同问题。

以下结果使用官方编码实现及发布的 124M 分词数据实际核验，全部可精确解码回原文：

| 输入 | 预分块 | 实际词元 | 词元 ID |
| --- | --- | --- | --- |
| `apple&dog` | `apple`、`&`、`dog` | `apple`、`&`、`dog` | `[18040, 5, 9703]` |
| `apple,dog` | `apple`、`,`、`dog` | `apple`、`,`、`dog` | `[18040, 11, 9703]` |
| `apple, dog` | `apple`、`,`、` dog` | `apple`、`,`、`Ġdog` | `[18040, 11, 3290]` |
| `apple , dog` | `apple`、` ,`、` dog` | `apple`、`Ġ,`、`Ġdog` | `[18040, 837, 3290]` |
| `&&` | `&&` | `&&` | `[25226]` |
| `,!` | `,!` | `,`、`!` | `[11, 0]` |

前三种输入都不能在 GPT2 的这套规则下成为一个词元。逗号后是否有空格，会改变后一个词元：`dog` 与 `Ġdog` 是不同词元；空格不被丢弃，也不会让逗号与字母跨块合并。空格也可附着到后面的符号块，如 `apple , dog` 中的 `Ġ,`。

**连续标点／符号可以处于同一个预分块，但同块不等于一个词元。**`&&` 实际合成一个词元，`,!` 虽然同块，却仍拆成两个词元；这取决于已学习的 BPE 合并规则，而不是逐个按标点种类切分。上述判断来自正则中的 ` ?[^\s\p{L}\p{N}]+` 分支及逐块调用 BPE 的编码流程。[官方分词实现](https://github.com/openai/gpt-2/blob/master/src/encoder.py)

核验日期：2026-10-11。其他分词器可能使用不同预分块规则，本节结论不能直接推广到全部语言模型。
